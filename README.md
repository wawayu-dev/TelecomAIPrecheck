# Telecom AI Precheck

面向电信运营商投诉处理场景的 AI 核查辅助系统。

> 工单流转后自动准备核查材料，AI 提供可追溯的辅助意见，最终结论始终由业务人员确认。

Telecom AI Precheck 以“增值业务扣费争议”为切入点，嵌入运营商已有客服和投诉工单流程，自动聚合账单、订购记录与授权凭据，执行确定性规则核验，调用科大讯飞星辰 MaaS 生成结构化建议，再交由投诉处理专员修订确认。

系统不重新建设 CRM 或呼叫中心，不让 AI 执行退款、套餐变更等高风险操作。当前仓库已经形成从工单流转、异步预处理、人工核查到质检审计的可运行闭环。

## 业务闭环

```text
客服提交投诉工单
        │
        ▼
宿主系统流转至投诉处理队列
        │  事件 ID + 工单 ID + 工单版本
        ▼
后台异步读取账单、订购和授权材料
        │
        ▼
证据快照 + 确定性规则核验
        │
        ▼
科大讯飞 MaaS 生成结构化辅助意见
        │
        ▼
结构校验 + 证据引用白名单校验
        │
        ▼
投诉处理专员修订并确认/退回
        │
        ▼
质检人员只读查看完整审计时间线
```

工单一旦进入投诉处理队列，AI 核查任务就会在后台自动执行。投诉处理专员打开工单时可以直接查看已经准备好的材料，不需要额外点击“生成 AI 建议”，也不需要停留在页面等待模型响应。

## 已实现能力

### 自动核查

- 宿主工单事件驱动的异步预处理
- 账单、订购记录和授权凭据自动聚合
- 授权缺失、金额不一致和证据关联检查
- 科大讯飞星辰 MaaS / 星火模型接入
- 结构化 AI 摘要、证据引用和处理建议
- 当前有效结果与历史工单版本管理

### 人工决策

- 投诉处理专员查看原始材料和核查时证据快照
- 修订核查摘要、处理建议和核查依据
- 确认核查材料或要求补充材料
- AI 调用失败时直接转人工处理
- 数据库版本控制，防止重复和并发覆盖

### ToB 可靠性

- `OPERATOR`、`REVIEWER`、`AUDITOR`、`HOST` 角色权限
- Session、CSRF 和服务身份校验
- 工单事件幂等、有限重试和中断恢复
- 模型超时、非法响应、虚构证据引用的安全兜底
- 证据快照、模型、Prompt、人工意见和 Trace ID 全程留痕
- 审核结果与审计记录的事务一致性
- 手机号、身份证号和邮箱保存前脱敏

### 工程交付

- MySQL、Spring Boot、Vue/Nginx 整栈 Docker Compose
- 前后端健康检查和统一 Nginx 入口
- 后端单元/集成测试、前端组件测试和浏览器流程测试
- GitHub Actions 版本标签构建与整栈验收
- BuildKit 缓存加速 Docker 镜像构建

## 三类业务角色

| 角色 | 页面任务 | 权限边界 |
| --- | --- | --- |
| 客服受理人员 | 登记投诉并提交至投诉处理队列 | 不查看 AI 核查结果和审计日志 |
| 投诉处理专员 | 核对证据、修订 AI 建议并确认或退回 | 不执行退款，不修改原始证据快照 |
| 质检审核人员 | 只读查看核查结果和完整操作时间线 | 不参与业务确认，不修改业务数据 |

质检审核人员不是投诉流程中的第二审批节点，而是独立的只读监督角色。

## AI 如何避免“编造证据”

系统没有把所有材料直接交给模型后原样展示回答，而是建立了多层约束：

1. **事实来自宿主系统：** 投诉、账单、订购和授权材料由 `TicketContextProvider` 提供。
2. **规则先于模型执行：** 证据缺失、关联错误和金额差异先由 Java 代码确定性检查。
3. **输出字段白名单：** 模型只能返回投诉类型、争议金额、摘要、证据 ID 和有限的核查建议。
4. **证据引用校验：** 模型引用的每一个证据 ID 都必须存在于本轮不可变快照中。
5. **缺失证据中性化：** 授权材料不完整时，后端强制使用“需要人工核验”的中性结论。
6. **高风险操作隔离：** 模型输出结构中不存在退款金额、违规认定或外部执行动作字段。

核心原则是：**业务事实由宿主系统提供，确定性规则由代码执行，AI 负责理解和整理，最终意见由人确认。**

## 异步任务与失败兜底

```text
QUEUED ──► RUNNING ──► COMPLETED
               │
               ├─ 临时失败 ──► RETRY_WAIT ──► RUNNING
               │
               └─ 永久失败/次数耗尽 ──► FAILED ──► 人工接管
```

- 同一宿主、工单和业务版本只创建一轮任务。
- 同一事件 ID 不能被用于不同工单版本。
- 新版本到达后，旧结果继续保留用于追溯，但不能再被确认。
- 模型调用和宿主查询不占用长数据库事务。
- 线程池饱和或进程中断后，数据库扫描器可以恢复未完成任务。
- AI 服务不可用不会回滚宿主系统已经完成的工单流转。

## 技术架构

```text

   │
   ▼
Nginx + Vue 3 + Vue Router
   │  /api、/actuator
   ▼
Spring Boot 3.5 + Spring Security
   ├── MyBatis + Flyway ───────────► MySQL 8.4
   ├── TicketContextProvider ──────► 宿主工单/账单/订购/授权系统
```

## 一键启动

### 环境要求

- Docker Engine
- Docker Compose v2

### 启动整套系统

```sh
scripts/demo.sh up
```

首次启动会：

1. 自动生成本机随机数据库密码和演示身份密码；
2. 构建后端与前端镜像；
3. 启动 MySQL、Spring Boot 和 Nginx；
4. 等待三个服务全部通过健康检查。

启动完成后访问：

- 业务页面：http://127.0.0.1:8088
- 健康检查：http://127.0.0.1:8088/actuator/health

常用命令：

```sh
scripts/demo.sh status   # 查看服务状态
scripts/demo.sh logs     # 查看前后端日志
scripts/demo.sh build    # 只构建镜像
scripts/demo.sh stop     # 停止容器，保留 MySQL 数据卷
```

未配置讯飞模型凭据时，系统仍可完整演示“AI 失败后转人工处理”的降级闭环。配置 `XFYUN_API_KEY` 和 `XFYUN_MODEL` 后，新工单会调用真实模型。

## 合成演示场景

| 工单 | 场景 | 预期核查方向 |
| --- | --- | --- |
| `DEMO-001` | 账单、订购和授权材料齐全 | 展示完整证据核查和人工确认 |
| `DEMO-002` | 查询成功但未找到授权凭据 | 提示进一步核验，不认定违规扣费 |
| `DEMO-003` | 账单 30 元、订购月费 20 元 | 提示核实计费依据，不自动计算退款 |

所有客户、工单、账单和授权材料均为合成数据。

## 项目边界

这是面向运营商典型扣费争议场景的工程演示项目，不是科大讯飞或电信运营商的官方产品，也不是生产系统。

当前已经验证的是：一个小业务单元如何以低侵入方式接入既有系统，并在 AI 不可靠或不可用时仍保持人工可处理、证据可核验、过程可追溯。

当前不包含：

- 真实运营商生产工单和业务接口
- 自动退费、订购修改或其他资金/业务操作
- 生产级统一认证、租户隔离和工单级数据权限
- 防篡改存证平台、等保或运营商终验结论
- 基于真实业务样本的准确率和效率收益结论

后续生产化工作的重点不是继续增加 AI 功能，而是接入真实业务契约、完善组织与数据权限、建立效果评测集，并补充监控、限流、告警和合规留存策略。
