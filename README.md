# Telecom AI Precheck

**面向电信运营商的 AI 工单预审模块**

> 小业务闭环 · 低侵入集成 · 人工决策 · 全程可追溯

Telecom AI Precheck 是一个基于 **Java 17、Spring Boot、Spring AI 与科大讯飞星辰 MaaS** 构建的轻量化、可嵌入式 AI 业务模块。

项目面向电信运营商**已有的客服／投诉工单系统**，以**增值业务扣费争议**为切入点，帮助工单处理人员完成投诉信息整理、收费与订购证据预核验、预审意见生成和人工复核。它不替代原有工单系统，更不让 AI 直接决定退费。

**项目状态：Issue #1 已完成；Issue #2 后端预审链路已实现，spark-x2.5 真实联调已通过；人工审核尚未实现。** 本 README 同时说明设计目标与计划验收项；未勾选的能力不代表已经实现或上线。

## 1. 为什么做这个模块？

当用户投诉“我没订购视频会员，为什么这个月扣了 30 元？”时，客服或投诉处理人员往往需要把自然语言诉求整理成标准字段，再核对账单、订购记录及授权凭据，形成可交接的处理意见。

本模块聚焦这一段**重复的信息整理与证据准备工作**：

- **减少重复整理：** 提取争议业务、账期、金额、客户诉求，并生成规范化摘要。
- **提前识别缺失信息：** 关联已有业务证据，提示尚未找到的关键凭据。
- **降低交接成本：** 向人工审核员交付可核对、可修订的预审结果，而不是一段不可验证的 AI 回答。
- **保留责任边界：** 证据、模型建议和人工结论分开保存，关键操作全程留痕。

以上是**待验证的业务价值假设**，并非已实现的效率提升。项目将通过合成工单样本和实际耗时、结果校验来评估效果。

## 2. 一个具体的业务场景

**客户投诉：**“这个月多扣了 30 元视频会员费，我没有主动办理，要求核实。”

**宿主系统提供的模拟证据：**

| 证据 | 示例内容 | 当前状态 |
| --- | --- | --- |
| 账单明细 `BILL-001` | 2026-10，视频会员，30.00 元 | 已找到 |
| 订购记录 `ORDER-001` | 有对应增值业务订购记录 | 已找到 |
| 授权凭据 | 用户确认订购的可核验凭据 | 未找到 |

**预审模块的输出：**

1. AI 识别诉求并生成简明摘要：这是一起增值业务扣费争议。
2. 后端基于实际返回的证据检查完整性，标记“授权凭据缺失”。
3. AI 生成**建议人工进一步核验授权**的处理意见；不认定违规扣费。
4. 审核员查看证据及预审意见，修订或确认后，将结果交回原有工单流程。
5. 模块记录证据快照、模型信息、审核人、时间、状态变化和关联 Trace ID。

**核心原则：业务事实由宿主系统提供，AI 负责辅助理解，规则由代码执行，最终业务意见由人工确认。**

## 3. MVP 功能边界

| 必须完成 | 明确不做 |
| --- | --- |
| 读取宿主工单及模拟业务证据 | 重新建设完整 CRM／客服工单平台 |
| 使用讯飞 MaaS 生成结构化预审意见 | 自动退费、修改资费或真实订购状态 |
| 证据引用校验与缺失项检查 | 多智能体、复杂工作流编排 |
| 人工复核、状态约束与并发保护 | 语音识别、语音合成、客服质检 |
| 业务审计、异常兜底、基础测试 | 为展示技术栈而引入微服务、MQ、向量库 |
| Vue 3 单页面与宿主路由接入示例 | 完整运营分析后台 |

**一个页面、三个主要操作：生成预审 → 人工复核 → 查看审计。**

## 4. 业务流程与安全边界

```text
宿主工单详情页
    │ 点击「AI 预审」，传入 ticketId
    ▼
TicketContextProvider
    │ 从宿主读取投诉、账单、订购和授权证据（Demo 使用模拟适配器）
    ▼
证据快照 + 确定性规则核验
    ▼
Spring AI → 讯飞星辰 MaaS（星火模型）
    │ 诉求分类、信息提取、摘要与建议
    ▼
结构校验 + 证据 ID 白名单校验
    ▼
人工复核（可以修订／确认／退回）
    ▼
形成可供宿主继续处理的预审结果 + 审计记录
```

### 必须满足的约束

- **证据可信：** AI 引用的证据 ID 必须存在于本次预审快照中；证据缺失就明确标记，不得补造事实。
- **人工决策：** 模型输出是建议，不触发退费、套餐变更或其他外部业务操作。
- **状态受控：** 未进入待审核状态不得提交审核；同一轮预审不能被并发重复确认。
- **异常可恢复：** MaaS 超时、响应异常或结构解析失败时，保留工单与失败记录，允许人工接管。
- **操作可追踪：** 记录操作者、动作、时间、前后状态、关联证据及 Trace ID；审核状态更新与审计写入保持事务一致。
- **数据最小化：** 开发与演示只使用合成数据；API Key 使用环境变量，日志不输出密钥或不必要的客户原文。

> 审计表采用追加写入、不提供业务删除／修改接口；这**不等于**具备生产级防篡改能力。生产接入仍需要统一认证、细粒度权限、租户隔离与合规留存策略。

## 6. 低侵入集成设计

模块**不拥有客户、账单、订购和原始工单主数据**，只持久化自己的预审、审核及审计记录。

后端通过宿主适配契约获取业务上下文：

```java
public interface TicketContextProvider {
    TicketContext getContext(String ticketId);
}
```

- **演示环境：** `MockTicketContextProvider` 提供可重复测试的合成工单与证据。
- **现有业务系统：** 实现相同接口，从既有 Service 或业务 API 读取数据，无需改动 AI 预审核心逻辑。
- **前端：** 在现有 Vue Router 注册预审页，由工单详情页传入 `ticketId`，复用宿主的认证与权限上下文。
- **结果交接：** 模块提供结构化预审查询接口，由宿主按其原有流程继续流转工单。

目标是在**约定好技术版本、数据契约、认证和权限接口的模拟宿主**中，以极少的配置完成接入，并录制实际集成过程。**“五分钟集成”是待测试的演示目标，不是对任意企业系统的承诺。**

## 7. 主要接口（规划）

| Method | Endpoint | 说明 |
| --- | --- | --- |
| `POST` | `/api/ai-prechecks/tickets/{ticketId}` | 发起一轮预审 |
| `GET` | `/api/ai-prechecks/tickets/{ticketId}` | 查询该工单的预审历史与最新结果 |
| `POST` | `/api/ai-prechecks/{precheckId}/reviews` | 审核、修订或退回预审意见 |
| `GET` | `/api/ai-prechecks/{precheckId}/audits` | 查看审计事件 |

> 接口仅用于本项目 MVP，最终参数与路径以实际实现及接口测试为准。提交人工审核时，审核员身份必须由服务端认证上下文确定。

## 8. 数据与可追溯性

模块最终计划维护以下核心表；Issue #2 已实现 ai_precheck_run，并以独立 ai_precheck_evidence_snapshot 表保存快照，审核与审计表在 Issue #3 实现：

| 表 | 记录内容 |
| --- | --- |
| `ai_precheck_run` | 宿主工单 ID、模型与 Prompt 版本、证据快照、AI 输出、调用结果、Trace ID |
| `ai_precheck_review` | 预审 ID、审核人、修订后的意见、审核决定与时间 |
| `ai_precheck_audit` | 操作主体、事件类型、状态变更、时间、关联 Trace ID |

**预审状态（规划）：** `CREATED → ANALYZING → PENDING_REVIEW → REVIEWED`。

模型调用失败时，调用结果记为 `FAILED`，工单预审仍进入人工待审核状态，避免业务被 AI 服务可用性阻塞。审核操作使用数据库事务和条件更新／乐观锁避免重复提交。

## 9. 测试与业务价值验证

**关键自动化测试：** 正常预审、缺失证据、非法证据引用、模型超时／无效响应、无权限审核、重复或并发审核、审计事务回滚。

**小样本验证（计划）：** 使用约 20 条人工标注的**合成**扣费争议工单，记录：

- 关键字段提取正确率；
- 缺失证据识别情况；
- 人工修改预审内容的比例；
- 手工准备与 AI 辅助加人工复核的总耗时。

不预设准确率、节省时长或成本收益；结果完成测量后再填入 `docs/evaluation.md`。合成样本评测不能代表真实运营商生产效果。

## 11. 项目定位与声明

- 这是**针对运营商典型收费争议场景的学习与工程演示项目**，并非科大讯飞或电信运营商的官方产品。
- 业务规则、工单、客户标识、账单与授权凭据均为模拟内容，不连接真实运营商生产系统。
- AI 只辅助预审；真实扣费争议的调查、认定及后续处置由有权限的业务人员和现有流程完成。
- 项目刻意不做“大而全”的 AI 客服平台，优先验证**一个小业务单元的完整性、严谨性、可追溯性和可集成性**。

---

**项目目标：用一个真正可以运行和验证的小模块，展示 AI 能力如何可靠地融入既有 To B 业务系统。**
